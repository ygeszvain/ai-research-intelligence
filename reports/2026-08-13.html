Independent Analysis

Executive summary

The papers jointly move evaluation from isolated output quality toward composed system behavior. The skills study shows that topically relevant procedural context can cause wrong implementations or more than double cost. VAKRA shows that agents that appear competent on endpoint-style tool use still fail when APIs, retrieval, and natural-language policies must be composed. EnterpriseRAG finds a parallel collapse: models satisfy most individual constraints but rarely satisfy all of them together, while evidence gaps and contradictions trigger severe over-answering.

This is methodologically meaningful rather than a new capability jump. The common enterprise lesson is that adding more context, tools, or written policy does not monotonically improve reliability. Architecturally, the model should sit inside a governed execution system that checks applicability, preserves task invariants, traces evidence influence, replays tool calls, and scores whole-workflow compliance. The immediate opportunity is controlled evaluation infrastructure, not autonomous production expansion.

1. Agent Skills Can Be Harmful: An Empirical Study of Skill-Induced Failures in LLM Agents

Gen Dong, Yanjie Gao, Liqun Li, Tianyin Xu, Yu Hua, Fan Yang · Microsoft Research/Microsoft, UIUC, HUST

IdentifierarXiv:2608.11888
Categorycs.AI
SubmittedAug 12, 2026, 10:15:19 UTC
Statusv1; not peer reviewed

Abstract · PDF · Full text · Artifact not found No official code/data release was verified.

A skill should be treated as executable policy whose causal value must be tested against no-skill and matched-skill controls, because relevant-looking guidance can both break tasks and induce large hidden costs.

Problem and contributions

Paper Fact The paper audits SkillsBench (84 tasks, 11 domains) and SWE-Skills-Bench (490 repository tasks), expanding the comparison space from 826 to 20,664 possible pairs by adding semantically matched public skills. Runs hold the model, task, verifier, environment, and harness fixed while varying skill setup.

Independent Analysis The main novelty is not the failure taxonomy alone; it is the differential-testing design that treats a successful no-skill or alternative-skill run as a pseudo-oracle.

Technical approach

OpenCode 1.15.1 with Claude Opus 4.6 executes target and reference runs. A functional failure is skill-run FAIL/reference PASS. An efficiency regression requires both token use and runtime to increase, with at least one exceeding 2×. Manual consensus labels trace divergences; SkillTriage then extracts structured differential evidence and predicts taxonomy labels using GPT-5.5 with 2-of-3 voting.

Architecture and workflow

Paper-derived architecture; the reference is a pseudo-oracle, not ground truth.

Results and evidence strength

Paper Fact Final dataset: 307 attributed failures—125 functional and 182 high-confidence cost regressions. Of functional failures, 86/125 were task-implementation faults. Of cost regressions, 114/182 were excessive procedure; excessive verification alone accounted for 67. SkillTriage matched exact manual labels on 111/125 functional cases and 132/182 cost cases.

No repeated-seed uncertainty is reported for the underlying agent runs. Deterministic verifiers strengthen outcome measurement, but one frontier model/harness limits generalization. Primary evidence.

Risks and limitations

  • Authors: manual trace attribution is subjective; findings may depend on benchmark, harness, model, and skill ecosystem.
  • Independent: successful paired runs do not eliminate stochastic model variance; public-skill retrieval may overrepresent low-quality skills.
  • Reproducibility: no official analysis dataset or SkillTriage code was verified.
  • Security: third-party skills can encode dependencies, paths, or hidden behavior that must be treated as supply-chain inputs.

Human review remains required for promotion.

2. VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

Ankita Rajaram Naik, Anupama Murthi, Benjamin Elder, Siyu Huo, Raavi Gupta, Abhinav Jain, Praveen Venkateswaran, Abdulhamid Adebayo, Danish Contractor · IBM

IdentifierarXiv:2608.12282
Categorycs.AI
SubmittedAug 12, 2026, 17:27:27 UTC
Statusv1; not peer reviewed

Abstract · PDF · Full text · Verified code · Verified dataset · CC BY-NC-SA 4.0

VAKRA turns enterprise-like API/RAG workflows into replayable executable tests, revealing that the decisive bottleneck is cross-source language reasoning and policy judgment rather than basic tool invocation.

Problem and contributions

Existing benchmarks usually isolate function calling, retrieval, or policy adherence. VAKRA composes them: 8,000+ locally hosted APIs over 62 BIRD-SQL domains; domain-aligned retrieval collections; 2–5-hop tasks; and policies that can forbid a source or render a question unanswerable. Predicted tool calls are replayed against executable environments, allowing multiple valid paths.

Technical approach

BIRD-SQL databases are transformed into slot/selection and dashboard-style APIs. ClapNQ and Wikidata5M seed ChromaDB collections. A fixed LangGraph ReAct harness communicates with typed tools over MCP. Evaluation is a waterfall: replayed tool-sequence containment, grounded final-answer judging, then deterministic policy-trace validation. GPT-OSS-120B serves as the temperature-zero judge for semantic cases.

Architecture and process

Paper-derived architecture. Enterprise placement: sandbox benchmark environment beside—not inside—the production control plane.

Results and evidence strength

Paper Fact GPT-5.5 led the reported aggregate settings but reached 70.4% on endpoint-style APIs, about 50–51% on compositional BI APIs, and 26.0% in multi-source multi-hop evaluation. On questions where policy makes the task unanswerable, success was 3.7% for GPT-5.5 and 2.4% for Claude Opus 4.7. Entity disambiguation on the combined set was 59.56% for GPT-5.5.

The executable code, dataset, splits, Docker environment, evaluator, and tests are public. Human-evaluation agreement is mixed: cross-source entity consistency had κ=.868, but several subjective criteria had near-zero or negative κ, weakening confidence in those qualitative checks. Primary evidence.

Risks and limitations

  • Generated workflows inherit assumptions from BIRD-SQL, Wikipedia-derived content, and generation judges.
  • The fixed ReAct harness isolates models but may understate gains from planning, memory, or specialized routing.
  • Semantic waterfall gates depend on GPT-OSS-120B judgment; some human agreement statistics are weak.
  • Closed-model comparisons have cost/subset asymmetries; Claude Opus was evaluated on a subset.
  • CC BY-NC-SA licensing affects commercial reuse.

Feed traces to observability and policy systems; never connect benchmark agents to live write-capable tools. Use workflow-class routing rather than a single model leaderboard.

3. EnterpriseRAG: Benchmarking LLM Instruction Adherence and Robustness under Non-Ideal Enterprise Retrieval

Huiqi Miao, Xinbao Sun, Bo Wang, Fanyu Meng, Lijun Mei, Na Wu, Di Jin, Chao Deng, Junlan Feng · Jiutian Research, China Mobile

IdentifierarXiv:2608.11584
Categorycs.AI
SubmittedAug 12, 2026, 02:51:04 UTC
Statusv1; not peer reviewed

Abstract · PDF · Full text · Not publicly available benchmark/evaluation promised upon publication; raw logs cannot be released.

Enterprise RAG reliability is a conjunctive problem: high average compliance with individual constraints hides severe failure when all evidence, formatting, persona, citation, refusal, and conflict-handling requirements must hold simultaneously.

Problem and contributions

Clean-context QA benchmarks do not capture production retrieval noise, missing evidence, factual conflicts, and multi-dimensional instructions. EnterpriseRAG starts from 491 authentic de-identified queries and constructs 983 expert-validated instances in six domains, averaging 8.4 constraints per query.

The core contribution is a joint evaluation of RAG quality, loose per-constraint adherence, strict all-constraint adherence, rejection accuracy, and conflict recognition.

Technical approach

Each instance contains query, fused constraints, and retrieved documents. Hybrid BM25+dense retrieval creates noisy contexts; sparse gap/conflict cases are augmented under controlled procedures. Thirteen models are evaluated. Structural rules use programmatic checks; behavioral protocols use Kimi-k2-thinking. On 150 human-labeled samples, judge agreement was 88% and κ=.77; conflict recognition κ=.93.

Architecture and process

Paper-derived benchmark workflow. Enterprise placement: offline evaluation between retrieval pipeline changes and release approval.

Results and evidence strength

Paper Fact On noisy retrieval, Qwen3-235B-Thinking achieved 83.8% loose IAS but 26.8% strict IAS. Claude Opus 4.5 had the best knowledge-gap rejection accuracy at 42.7%. DeepSeek-R1 led conflict recognition at 44.3%; GPT-4.1 reached 18.5%. Explicit protocols significantly improved conflict recognition across all 13 models, but rejection improved significantly for only 2/13.

Natural-versus-synthetic conflict tests found no significant difference on conflict recognition (p=.120) or strict IAS (p=.826), but synthetic conflicts were less faithful, so ecological equivalence is only partial. Primary evidence.

Risks and limitations

  • Authors: text-only RAG, reasoning-model evaluator bias, binary strict metric.
  • Independent: 94.7% of gap cases and 91.3% of conflict cases were augmented; observed protocol effects are not randomized.
  • Raw logs are unavailable and promised benchmark artifacts are not yet public.
  • The “orchestration gap” is sensitive to constraint count and metric design; it is not direct production failure probability.
  • Domain and language coverage may not generalize internationally.

Emerging pattern

Reliability falls at composition boundaries: reusable instructions meet task specifics, one tool’s output becomes another’s input, and individually satisfied constraints must hold jointly.

Contradiction and tension

More guidance can help conflict recognition, yet skills show that added procedure can cause failures and cost. The missing variable is conditional applicability: when, where, and how much guidance to enforce.

Unresolved gap

No benchmark unifies causal skill selection, cross-tool authorization, retrieval evidence sufficiency, and production-shift reliability under one controlled design.

Synthesized enterprise architecture — Independent Analysis

Not demonstrated by any single paper. Combines skill compatibility, evidence sufficiency, typed least-privilege tools, replayable traces, and strict/differential evaluation.

Knowledge reinforcement

Key concepts

Differential skill testing: varying skill context while holding the task, agent, environment, and verifier fixed.

Pseudo-oracle: a successful comparison run showing solvability, without claiming to be the unique correct solution.

Waterfall evaluation: ordered gates that attribute failure to the earliest unsuccessful stage.

Strict IAS: a binary test that passes only when every applicable instruction constraint is satisfied.

Evidence sufficiency: whether retrieved material is adequate to justify an answer—not merely topically related.

Recall questions

  1. Why does a topically relevant skill still require a no-skill control?
  2. What does VAKRA’s policy-unanswerable result reveal that ordinary function-calling benchmarks miss?
  3. Why can 83.8% loose instruction adherence coexist with only 26.8% strict adherence?
  4. Which parts of today’s evidence rely on LLM judges, and how does that limit confidence?
  5. How would you combine skill compatibility, retrieval sufficiency, and tool-policy checks without making the workflow excessively expensive?

90-second teach-back

Explain to an executive why agent reliability should be evaluated at composition boundaries. Use one skill-induced failure mechanism, one VAKRA degradation result, and the EnterpriseRAG loose-versus-strict gap; then name one reversible experiment.

Research connection

The skill paper applies differential testing and causal-control logic to context engineering. VAKRA resembles integration testing and event sourcing: the meaningful unit is a replayable trajectory across typed services. EnterpriseRAG is a reliability problem for a series system: when many individually reliable components or constraints must all succeed, overall success can collapse multiplicatively. Together they connect agent engineering to software verification, causal inference, measurement theory, database lineage, and organizational control design.

One idea to remember: Reliability must be measured where instructions, evidence, tools, and policies compose—not where each component looks good in isolation.
